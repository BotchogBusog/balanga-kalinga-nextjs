# Data Dictionary Prompt — Balanga Kalinga

Copy the prompt below into ChatGPT, Gemini, Claude, or another document AI to
generate a data dictionary in the same style as the sample image.

## Prompt

```text
Create a formal DATA DICTIONARY document for the database below. It is for a
capstone manuscript titled:

"Balanga Kalinga: A Web-Based Student Wellness Assessment and Counseling
Management System"

Follow this layout exactly, similar to a formal Word data-dictionary sheet:

1. At the top of EVERY table section, create a two-column header:
   - Left: "DATA DICTIONARY"
   - Right: "Reference Number: DD-01" (increase the number for every next table:
     DD-02, DD-03, and so on) and "Version Number: 1.0"
2. Under the header, show:
   - System Name: Balanga Kalinga: A Web-Based Student Wellness Assessment and
     Counseling Management System
   - Subject: [table name]
3. Below it, create a field-definition table with EXACTLY these columns:
   PK | FK | UK | Field Name | Data Type | Length | Nullable | Default Value |
   Description
4. Use "Yes" or "No" for Nullable. Use an em dash (—) as the Length for INT,
   DATE, DATETIME, TINYINT, and TEXT. Use the numeric length only for VARCHAR.
5. Place "Yes" in PK, FK, or UK only where that field has that property;
   otherwise use "No". UK means Unique Key. For auto-increment identifiers,
   include "AUTO_INCREMENT" in Default Value.
6. Use concise, clear, non-technical descriptions. Include one short sentence
   below every table explaining what that table stores and how the system uses it.
7. Make the output ready to paste into Microsoft Word: one table section per
   database table, clean headings, no SQL code, no Markdown code fences, and no
   invented fields.
8. Do NOT add pages, tables, or features that are not listed below. In
   particular, do not include journal entries, emergency resources, history,
   logs, audit tables, safety plans, self-care activities, payments, billing,
   receipts, or reports as database tables.

The system has EXACTLY these 7 active database tables and fields:

TABLE 1 — users
Purpose: stores student, counselor, and administrator account information for
registration, login, role-based access, and profile management.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- name: VARCHAR(120), NOT NULL
- email: VARCHAR(190), NOT NULL, UNIQUE
- student_id: VARCHAR(40), NULL, UNIQUE, default NULL
- password_hash: VARCHAR(255), NOT NULL
- role: VARCHAR(20), NOT NULL, default 'student'
- course: VARCHAR(120), NULL, default ''
- year_level: VARCHAR(40), NULL, default ''
- school: VARCHAR(120), NULL, default ''
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP
- counselor_id: INT, NULL, UNIQUE, default NULL; this is a logical reference to
  counselors.id that connects a counselor login account with its counselor
  profile. Mark FK as "Yes (logical reference)" in the FK column; do not claim
  it is physically enforced as a foreign-key constraint.

TABLE 2 — counselors
Purpose: stores counselor professional profiles, contact details, schedules,
and availability for appointment booking.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- name: VARCHAR(120), NOT NULL
- specialization: VARCHAR(120), NOT NULL
- description: TEXT, NOT NULL
- schedule: TEXT, NOT NULL
- is_available: TINYINT, NOT NULL, default 1; 1 means available and 0 means
  unavailable
- email: VARCHAR(190), NULL, default NULL
- phone: VARCHAR(40), NULL, default NULL

TABLE 3 — appointments
Purpose: stores counseling appointment requests and their transaction reference
numbers. This is a booking feature only; it does not process payments.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- transaction_ref: VARCHAR(50), NULL, UNIQUE, default NULL; generated by the
  current booking workflow in the format BK-YYYYMMDD-XXXXXXXX
- user_id: INT, FK to users.id, NOT NULL
- counselor_id: INT, FK to counselors.id, NOT NULL
- requested_date: DATE, NOT NULL
- requested_time: VARCHAR(20), NOT NULL
- method: VARCHAR(30), NULL, default 'In-person'
- notes: TEXT, NULL, default NULL
- status: VARCHAR(30), NULL, default 'pending'; allowed values are pending,
  approved, declined, cancelled, and completed
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP

TABLE 4 — wellness_assessments
Purpose: stores a student's completed 10-question wellness-check result and
the calculated risk feedback.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- user_id: INT, FK to users.id, NOT NULL
- answers: TEXT, NOT NULL; stores the submitted wellness answers
- overall_level: VARCHAR(40), NOT NULL; stores low, moderate, or high risk
- summary: TEXT, NOT NULL
- suggested_actions: TEXT, NOT NULL
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP
Relationship behavior: when its user is deleted, this record is deleted too
(ON DELETE CASCADE).

TABLE 5 — moods
Purpose: stores the mood check-ins submitted by students from the dashboard.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- user_id: INT, FK to users.id, NOT NULL
- mood: VARCHAR(30), NOT NULL
- note: TEXT, NULL, default NULL
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP
Relationship behavior: when its user is deleted, this record is deleted too
(ON DELETE CASCADE).

TABLE 6 — ai_conversations
Purpose: stores each AI wellness-companion conversation created by a student.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- user_id: INT, FK to users.id, NOT NULL
- title: VARCHAR(200), NULL, default 'Talk with Kalinga AI'
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP
Relationship behavior: when its user is deleted, this record is deleted too
(ON DELETE CASCADE).

TABLE 7 — ai_messages
Purpose: stores individual student and AI messages within an AI conversation.
Fields:
- id: INT, PK, NOT NULL, AUTO_INCREMENT
- conversation_id: INT, FK to ai_conversations.id, NOT NULL
- role: VARCHAR(20), NOT NULL; identifies whether the message is from the user
  or the assistant
- content: TEXT, NOT NULL
- created_at: DATETIME, NOT NULL, default CURRENT_TIMESTAMP
Relationship behavior: when its AI conversation is deleted, this record is
deleted too (ON DELETE CASCADE).

Final validation before output:
- There must be exactly 7 Subject sections: users, counselors, appointments,
  wellness_assessments, moods, ai_conversations, and ai_messages.
- There must be no eighth table and no database table named reports.
- Keep every field name exactly as written.
```

## Quick check for the generated result

It is correct only if it has:

- 7 subject/table sections (`DD-01` through `DD-07`)
- The nine columns shown in the prompt
- `appointments.transaction_ref` marked unique
- `users.counselor_id` described as a **logical** reference
- No journal, emergency-resource, history, log, safety-plan, self-care, payment,
  billing, receipt, or report table
